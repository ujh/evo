# Experiment reference

Detailed runner, scoring, storage, and benchmark behavior. Read the relevant section when changing experiments or their results. For the genome and feature settings, see [The evolving genome](genes.md) and [Go features](features.md).

## Game results

- Every tournament game is played by the arena (`arena --mixed`, below); only the checkpoint benchmark still plays through `gogui-twogtp`. A GoGui `.dat` file is tab-separated: `GAME RES_B RES_W RES_R ALT DUP LEN TIME_B TIME_W CPU_B CPU_W ERR ERR_MSG`.
  - Columns can be empty, so split on tabs. The benchmark does this in `ruby/game_result.rb`.
  - The benchmark saves twogtp's stderr to `PREFIX.err` next to the `.dat` file while the game runs. Only stderr says which program crashed ("Black program died" or "White program died").
- Each experiment stores its opponents, its benchmark panel, and its scoring when it is created (tables `opponents`, `benchmark_opponents`, and `scoring`, from `SetupExperiment::DEFAULT_OPPONENTS`, `DEFAULT_BENCHMARK`, and `DEFAULT_SCORING`), and the runner reads them from there, so changing the defaults only affects new experiments. By default every win is worth 1 point, whether the loser is a network or a bot, a draw 0, and the odd player out in a round sits out with 0. `scoring['rules']` is the version of the scoring logic (`RunGeneration::SCORING_RULES`); bump it when `score_game`, `points_for`, or `ArenaResult` change what counts or what stops a run, and an experiment begun under other rules refuses to run. Rules `3` put every tournament game in the arena; experiments created under rules `2`, such as `bigrun` and `even-bigger`, continue only from a checkout before that change (`git checkout 2568fff~1`); the current runner migrates their database, then refuses to run it. The bots play in the ranking like networks, and against each other, on purpose: their place in the ranking shows how the networks compare to them. Parents are chosen by tournament selection (`select_parent` in `ruby/run_generation.rb`): draw `tournament_size` networks (setting, default 3) with replacement and keep the highest score. Only the order of scores matters, and equal scores pick uniformly.
- Every game is area-scored with the experiment's komi (the `komi` setting, a multiple of 0.5 from −50 to 50, default 6.5, so a margin is never 0 without a draw). The arena gets it as KOMI for every tournament game and sends it to each bot with `komi`; the benchmark passes it as `-komi` to `gogui-twogtp`, which sends it to both players and the referee. The benchmark's referee, `GameResult::REFEREE`, is GNU Go with `--chinese-rules` (the benchmark appends its `--seed`); GNU Go players keep their own rules. An experiment created before the setting has no `komi` and refuses to load.
- Scoring rules (agreed with the owner; rules `3`, in `score_game` and `points_for` in `ruby/run_generation.rb` and in `ruby/arena_result.rb`):
  - The arena's Tromp–Taylor count decides every tournament game, with a bot or not (`scorer` `tromp_taylor`); in the benchmark, the GNU Go referee (Chinese rules) decides. A win (`B+` or `W+`) counts, including games stopped by the move limit, which the arena counts as the board stands, dead stones included. How often the two scorers pick different winners on the same games is below.
  - A draw gives no points.
  - A bot that resigns loses (`B+R`/`W+R`, `end_reason` `resign`), whoever its opponent. A network that takes more than its main time, `game_length` minutes for all its moves of the game, loses (`B+T`/`W+T`, `end_reason` `time`), and so does a network the arena cannot load (missing, unreadable, or not fitting the board; `end_reason` `network_error`).
  - A game the arena could not finish is never scored or stored: a bot that missed a deadline, took its side past main time, played an illegal move, crashed or answered with a GTP error, or could not be started (failure records `timeout`, `illegal`, `crash`, `launch`), a game neither network can load, and a game without a valid record (the arena died, or its output is cut off, duplicated, or malformed). The runner stores the chunk's other games, sends SIGTERM to the round's other chunks still running (`WorkerPool#terminate`; their output is never read, nor their statuses, which would look like Ctrl-C, and their games stay pending), and exits 1 (`RunGeneration::ArenaStopped`, which `RunExperiment` prints on stderr without a backtrace). The report names the chunk, the generation, and the round (from 0, as in the game IDs), what went wrong (no header, output not finished, a failure record, the exit status or the signal that killed it), each withheld game with its end reason, failing side and message (or `no record`), and the chunk's stderr (the resume empties `work/`), then how many other chunks it terminated, and ends with "resume after fixing the cause". The withheld games stay pending, and a resume replays them with the same seeds; which chunk stops the run depends on which finishes first, which does not matter, since the pending games replay the same way. A chunk killed by SIGINT or SIGTERM, or exiting 130 or 143, is an interrupt instead (below), which the arena's own exits never are. So a broken bot stops the run instead of filling the ranking with games nobody won. A generation copies each opponent's command into its `players` rows when it starts, so a stopped generation resumes with the command it started with: fix the bot program, or edit that generation's `players` rows; changing `opponents` only affects later generations. Under rules `2`, such games were stored with a `failure` and no points and never retried.
- For a GoGui game (the benchmark's, and the smoke checks'), check `RES_R` and `ERR`, not only whether the game finished. A crashed player shows only in `ERR`, and a crashed referee only as `?` in `RES_R`. `scripts/smoke-external-tools.sh` checks both. Keep it that way when changing it.
- Brown and AmiGo play deterministically. The 5 Brown and 10 AmiGo "instances" are copies of the same opponent, so replaying a pairing with the same colors adds no information.
- GNU Go seeds its random choices from the clock unless it gets `--seed N`. The runner always passes one: in the tournament, each GNU Go bot's command in the arena's manifest gets the game's seed, `Seeds.gnugo(seed, 'game', generation, round, black, white)`. Outside the runner, compare GNU Go behavior with a fixed seed.

### Tromp–Taylor against the GNU Go referee on the same games

`mise exec -- scripts/compare-arena-scoring.rb [--lanes N] [--small] [--keep]` plays one fixed, seeded set of tournament-style 9×9 games (komi 6.5, 200 moves, 10 minutes each side) twice: through `arena --mixed` (600 s main time, 10 s response deadline and grace) and through `gogui-twogtp` with the runner's flags (`-time 10 -force -maxmoves 200`, the referee `GameResult::REFEREE --seed N`, GNU Go players seeded with the same N, as the tournament did through twogtp before rules `3`). The networks are the champions (first network by rank, as the benchmark picks it) of `bigrun` generations 0, 500, …, 5500 and 5750 and of `even-bigger` generations 0, 100, 200 and 300, and 4 random generation-0 networks of each, exported from the databases opened read-only; `evo` plays them under twogtp. Each network plays Brown, AmiGo and GNU Go level 0 with both colors; the bots play each other (each ordered pair; three seeds where GNU Go plays); 40 random network pairs play with both colors. The script fails if any game's moves or end differ, if the arena writes a failure record, if twogtp reports an error, or if the arena's result differs from a Tromp–Taylor recount of the final position (from GNU Go's `loadsgf` and `list_stones`). For each game it asks the seeded referee for `final_status_list dead`, `seki` and `dame` and the side to move, and sorts out why the referee's result differs. `--small` plays 49 games only, to try the script. The scratch files go in a temporary directory, deleted afterwards unless `--keep`.

Run on 28 Sep 2026 at `6156e4a` (the script's commit), 6 games at a time: 249 games in 199 s, and the same output on a second run. All 249 have identical moves and end in both. None reached the move limit and nobody resigned (GNU Go level 0 never did), so every game ended by two passes and the differences below are all scoring.

| Pairing | Games | Same result | Same winner, other margin | Winner changes | Mean \|margin difference\| |
| --- | ---: | ---: | ---: | ---: | ---: |
| network–Brown | 50 | 47 | 3 | 0 | 1.8 |
| network–AmiGo | 50 | 32 | 11 | 7 | 7.1 |
| network–GNU Go level 0 | 50 | 0 | 33 | 17 | 68.5 |
| bot–bot | 19 | 9 | 7 | 3 | 28.9 |
| network–network | 80 | 27 | 48 | 5 | 15.4 |
| all | 249 | 115 | 102 | 32 | 22.7 |

Why the referee differs, in the 134 games where it does (winner changes in brackets):

- **Dead stones left on the board** (99 [23]): taking GNU Go's dead stones off and counting Tromp–Taylor gives the referee's result exactly. Tromp–Taylor counts a dead stone for its owner and makes the region around it neutral; the referee removes it and gives the area to the other side. A game ends when both pass, and a network or GNU Go often passes with the opponent's dead stones still inside its area.
- **Dame** (11 [0]) and **dead stones and dame** (10 [4]): after the dead stones go, the rest is the neutral points (GNU Go's dame, touching both colors). Tromp–Taylor gives them to neither; GNU Go's Chinese-rules `final_score` counts as if they were filled in turn starting with the side to move, so an odd number of dame gives that side one point more. That rule, applied after removing the dead stones, reproduces these 21 results.
- **Judgement** (14 [5]; 3 without dead stones, 11 with): neither rule reproduces the referee. The differences are 1–3 points in 12 of them and 13 and 16 points in two short network–network games; presumably GNU Go's scoring play-out fills or captures otherwise than its status lists say (for example, a dame point that only one side can fill without self-atari), which the script does not model. No stones in seki were found.

Who gains, in the 24 network–bot winner changes: against AmiGo, all 7 go from the network (by the referee) to AmiGo (by Tromp–Taylor); in each, AmiGo's dead stones stay in the network's area (9–20 stones) because the network passed without capturing them. Networks won 23 of 50 AmiGo games by the referee and 16 by Tromp–Taylor. Against GNU Go level 0, all 17 go the other way: networks win 0 of 50 by the referee and 17 by Tromp–Taylor, because GNU Go passes with the network's dead stones (8–39) still in its area. Against Brown, which fills the board before passing, the winner never changed, and networks won 42 of 50 either way. The bot–bot winner changes are all games with GNU Go (GNU Go against Brown twice, against itself once); the four Brown and AmiGo pairings, the only ones the default panel plays, keep their winner (one AmiGo–AmiGo game moves a point by dame). Network–network games are already scored by Tromp–Taylor in the tournament, so their 5 changes are what a referee would have said, not a change of rules.

So with Brown and AmiGo, a Tromp–Taylor tournament rewards a network for capturing dead stones before it passes: against AmiGo it loses games the referee gives it. A GNU Go opponent scored by Tromp–Taylor would lose games it wins on the board, since it passes leaving dead stones; a panel with GNU Go needs another ending (for example, having bots play on until the dead stones are captured) or a referee.

## Running experiments

- On a first run, `mise run run NAME` prompts on STDIN for settings. To start without prompts, create the experiment first; `SetupExperiment::SETTINGS` lists every setting with its default and its type (a whole number, an even whole number, or a number, and its range; `mise run new-experiment` without arguments shows them). A value that does not parse strictly is refused when the experiment is created, and a prompt asks again. The database stores settings as strings; `SetupExperiment.parse` turns them into Integers and Floats on every load, so the runner never converts them itself, and test settings must be typed too:
  ```sh
  mise run new-experiment NAME --board-size 9 --population-size 4 --hidden-layers 1 --layer-size 10 \
    --cross-over-rate 0.5 --game-length 10 --max-moves 200 --tournament-rounds 1 --keep-every 0 --seed 3
  mise run run NAME 4 one-generation
  ```
  That runs one generation of 10 pairings (9 games plus a bye for the odd player out) in about a second, which makes it a good smoke run. Every game goes to the arena; with seed 3, one is between two networks and 8 have a bot (25 Sep 2026, and again with every feature group, the default, 26 Sep 2026); with most seeds the 4 networks meet only the 15 bots. `--keep-every 0` skips the benchmark, which would otherwise add 60 games at generation 0. Delete `experiments/NAME` afterwards. Running it again breeds and plays the next generation. `experiments/` is gitignored.
- `hidden_layers` and `layer_size` are generation 0's shape. `features` (default `all`) is the feature groups every network of the experiment sees: `none` (the stones alone, the control), `all`, or a comma-separated list of `shapes`, `tactics`, `last_move`, `liberties` in any order, each once; it is a `SetupExperiment::FeatureSet`, parsed strictly (by `FeatureGroups.normalize` in `ruby/feature_groups.rb`) to the genes line's form, `none` or the groups in their fixed order (`all` becomes `shapes,tactics,last_move,liberties`), which is what the database stores and what the genes lines are checked against. `meta_rate` is the τ of self-adaptive mutation, and the `initial_*` settings are the genes every generation-0 network starts with (ranges = the clamps in `lib/ann.h`): `initial_feature_step` (default 0.01, 1e-4–1) is generation 0's `feature_step`, and `initial_feature_noise` (default 0.3, 0–1), no gene, is the relative noise on generation 0's feature weights. `initial_weight_changes`, when not given, is computed at creation from the generation-0 shape and feature set as max(1, 0.0004 × total weights), the feature inputs counted (`FeatureGroups.total_weights`, which `SetupExperiment.total_weights` uses: 9×9 1×10 has 1,732 weights with `none` and 10,652 with `all`, so 4.26 changes; `features` comes before it in `SETTINGS` for that) (a `SetupExperiment::Derived` default, computed from the settings before it on both the prompt and the `new-experiment` path) and stored, so a later formula change never alters an existing experiment; a value above the network's total weights is refused. `max_hidden_layers` (default 4) and `max_layer_size` (default 200) bound the shapes structural mutation can reach; the generation-0 shape must lie within them (`max_layer_size` is checked against `layer_size` only when `hidden_layers` is above 0), and a shape above them is refused on every path: the prompts ask again, `new-experiment` fails, and loading fails. So networks of one experiment differ in shape: from generation 1 on, a mutated child can gain or lose a layer or a neuron per layer, and its `births` row has its `structure` and its new `layers` and `width`. Nothing in the runner, the arena, or the benchmark assumes the generation-0 shape except `initial_weight_changes`' check and the check that `initial-population`'s genes lines have that shape. A seeded run that exercises the genes quickly:
  ```sh
  mise run new-experiment NAME --board-size 9 --population-size 12 --hidden-layers 1 --layer-size 10 \
    --cross-over-rate 0.5 --game-length 10 --max-moves 200 --tournament-rounds 3 --keep-every 2 \
    --benchmark-games 2 --initial-structure-rate 0.3 --initial-activation-rate 0.2 \
    --max-hidden-layers 3 --max-layer-size 20 --seed 4242
  ```
  Six generations of it (concurrency 4, every feature group; 26 Sep 2026) produced all four kinds of structural change, shapes from 0×0 to 3×10 (a 0×0 network is the largest here, 79,950 weights, since all 974 inputs connect to the outputs), no failed game, 2.5–2.8 s per generation, 7–9 s with a checkpoint's benchmark, 15 s for generation 0, and the same births (every column), networks, games, rankings, and benchmark rows on a second run with the same seed. With the defaults (`initial_structure_rate` 0.02, crossover rate 0.5) a generation of 20 sees a structural change only every few generations, so a run meant to explore shapes needs a higher starting rate. Loading a database that lacks a setting fails with "… is missing"; so an experiment created before the feature settings (`features`, `initial_feature_noise`, `initial_feature_step`) does not load.
- An experiment directory holds only `experiment.sqlite3`, the scratch directory `work/`, and the executables. The runner works inside `work/`, which it empties at the start of every generation, and calls `../evo`, `../arena`, `../evolve`, and `../initial-population`. They are **copies** of the build output, made on the experiment's first run once its settings are known, so a rebuild does not change an experiment that has started; to run new code, start a new experiment. The Ruby runner is not copied: it runs from the checkout, so an experiment whose executables take other arguments than the runner passes cannot resume. One started before the genes settings (`meta_rate`, `initial_*`) is such a case: its settings lack them and its `initial-population` and `evolve` take the old arguments. Once the provenance is recorded, a missing executable stops the run instead of being copied again. The `provenance` table records what they were built from: the git revision, whether the checkout had uncommitted changes, and the external tools release.
- `RunGeneration#play_round` scores the bye at once and plays every other game in the arena (`../arena --mixed`, scored by Tromp–Taylor, `scorer` `tromp_taylor`), in at most `concurrency` chunks, each one `WorkerPool` job with the files `arena-K.txt` (the manifest: the chunk's networks by their file in `work/` and its bots by player name, then each game, ID from the game's file prefix, followed by the command of each of its bots, a GNU Go command with the game's `--seed`), `arena-K.out`, and `arena-K.err`. Games with a bot are dealt out in turn first, then the others, so chunks differ by at most one game and by at most one game with a bot, wherever the bots stand in the ranking. Every manifest is written before the first chunk starts, and a field the manifest cannot hold (empty, or with a tab or another control character, such as an opponent's command) raises `ArgumentError` before any game. Each side gets `game_length` × 60 s of main time; the bot response deadline and `genmove` grace are `RunGeneration::RESPONSE_DEADLINE` and `GENMOVE_GRACE`, 10 s each (why in `engine/arena.c`'s header comment). The wait loop counts chunks. When a chunk finishes, `ArenaResult.mixed_chunk` reads its output (as UTF-8 whatever the locale; bytes that are not UTF-8 are replaced before parsing), and every game with a valid record that is not a failure is scored, stored, and ranked. If the chunk wrote a failure record, is incomplete (no header, a missing, cut-off, duplicate, or malformed record, or no matching trailer), exited non-zero, or was killed by a signal other than SIGINT or SIGTERM (SIGKILL, SIGSEGV), the runner then stops as the scoring rules above say, leaving the chunk's files in `work/`; it sends SIGTERM to the chunks still running instead of waiting out their bots' deadlines, and their results are not read. The arena dies of the SIGTERM after killing its bots. A SIGKILL of the arena (by hand, or the system out of memory) leaves no time for that: a bot that exits at stdin EOF, as Brown, AmiGo, and GNU Go do, ends by itself, but one that ignores it keeps running and must be killed by hand. Otherwise the chunk's files are deleted. What an arena row holds is in the bullet on game results below; the chunk's overhead share is floored at 0. `SCORING_RULES` `3` is the version that plays every tournament game in the arena.
- Everything but a game's files in progress lives in `experiments/NAME/experiment.sqlite3`: the settings, and each generation's round, players, standings (`rankings`), and pending games. `RunGeneration#data` loads a generation's state in the shape `data.json` used to have once per session and keeps it in memory, which must always equal what `ExperimentDatabase#state` would load (string keys, pending games in order). `save_data` replaces the whole state in one transaction at setup and at each round's pairing. A scored game saves only what it changed (`RunGeneration#save_game`), in one transaction with its `games` row (a bye has none): its `pending_games` row goes, and `rankings` stays exact, rank for rank. When the ranking was in score-then-name order before the game, the players whose score rose move up and the rows they pass shift down one (`ExperimentDatabase#raise_in_ranking`; points are never negative); otherwise, as for the first game after a round's shuffled pairing or a resume that loaded one, the generation's `rankings` rows are rewritten once. Ctrl-C stops the runner after that transaction commits, so a finished game is kept. On resume, `setup_complete` skips creating or breeding the population, the runner starts from the last generation in the database, and a generation's games are skipped only once `round` reaches `tournament_rounds`. A checkpoint's benchmark runs after that check too, so a resumed checkpoint finishes its benchmark. `RunGeneration#call` returns `:already_done`, which makes a `one-generation` run go on to the next generation, only when the generation played no tournament game and no benchmark game.
- At the end of every generation the runner prints its timings (`ruby/generation_timings.rb`, the monotonic clock): a summary of two or three lines, then one machine-readable line to compare runs by. Nothing is stored. The line is `timings` and `key=value` fields, seconds with three decimals, in this order and only for the parts that ran in this session: `generation=N partial=0|1 setup=S`, then per round played `round_K=S worker_round_K=S ruby_round_K=S games_round_K=N failures_round_K=N` (K from 1), then over those rounds `tournament=S worker=S ruby=S games=N failures=N`, then `benchmark=S total=S`. `setup` is creating or breeding the population and exporting the networks (on resume only the export); a round runs from queueing its first game to pairing the next round; `worker` is the summed wall time of its pool jobs (arena chunks, more than the round's time when they run in parallel); `ruby` is the round's time the runner spent not waiting for a job (pairing, queueing, reading results, scoring, storing); `games` counts the games scored (byes not counted) and `failures` those with a failure (always 0 under rules `3`, where a failed game stops the run and the generation prints no timings); `benchmark` appears for a checkpoint whenever its benchmark code ran. `partial=1` marks a generation an earlier session began (its state was already in the database): its times cover only this session, and the summary says so. A generation stopped by Ctrl-C or an error prints nothing, and so does one this session had nothing left to do in (its tournament finished and no benchmark game left, as when a `one-generation` run re-enters the last finished generation), so every timing line is a generation that ran.
- Ctrl-C during "Generating population" kills the running `evolve` too, and the runner exits quietly as it does in the tournament (with exit 130 and a message when evolve's status shows the interrupt before the trap ran). Nothing is lost: the children bred so far are in `births` and `networks`, but the generation's setup is saved only after the last child, so a resume breeds every child again from the first, with the same seeds and the same parent draws, and overwrites those rows. An interrupted and resumed run gives the same births, networks, games, rankings, and benchmark rows as an uninterrupted one (checked twice mid-breeding, 25 Sep 2026, and again with every feature group, 26 Sep 2026).
- A game that was queued but not yet scored when the runner stopped (after Ctrl-C, or when a chunk stopped the run) is replayed from scratch on resume, in a fresh `work/`. The benchmark passes `-force` to twogtp, which deletes an existing `PREFIX.dat`, so a replayed benchmark game's `.err` is rewritten too.
- Generation 0 names networks `0001.ann`, `0002.ann`, and so on. Later generations use `0.ann`, `1.ann`, and so on.
- Game results live in `experiments/NAME/experiment.sqlite3`, through `ExperimentDatabase` (`ruby/experiment_database.rb`, Sequel on SQLite). After scoring a game, the runner writes its row, and deletes an arena chunk's files once all its games are stored. The row holds:
  - the players, whether each is a bot (`black_external`, `white_external`), the winner, the length, the result (`referee_result`: the Tromp–Taylor count, `B+R`/`W+R` for a resignation, `B+T`/`W+T` for a time loss; GNU Go's in rules-2 rows of games with a bot), the error message (`move limit exceeded` for a game stopped by the limit, the arena's message for a network it could not load; GoGui's in rules-2 rows), and stderr, which a rules-3 row never has: a chunk's stderr is shared by all its games, and a stop prints it. `failure` is always empty under rules `3`; rules-2 rows have the reason a game failed there, twogtp's stderr for a game with a bot, and the chunk's stderr for a failed arena game;
  - `scorer`, who decided the game: `tromp_taylor` for every arena game, and `gnugo` for a rules-2 GoGui game refereed by GNU Go. `ExperimentDatabase#record` refuses a row without one, and rows from before migration 009 got `gnugo`;
  - `end_reason` (migration 012), how an `arena --mixed` game ended: `passes`, `limit`, `resign` (a bot resigned; `referee_result` `B+R`/`W+R`), `time` (a network ran out of main time; `B+T`/`W+T`), or `network_error` (one network could not be loaded and lost). A failed game is never stored, so `timeout`, `illegal`, `crash`, `launch`, and `network_error` for both sides never appear: `ExperimentDatabase#record` requires one of the stored reasons for a `tromp_taylor` row and refuses any other value on every row. Rows from before rules `3` have none;
  - the timings. For a GoGui game (rules-2 rows), `duration` is the wall-clock seconds of the whole `gogui-twogtp` run, measured by `WorkerPool`, and `time_black`/`time_white` are the seconds each player spent answering `genmove`, from twogtp's `TIME_B`/`TIME_W`, to a tenth; the rest of `duration` is the referee, the JVM, process starts, and the other GTP commands, plus a 3 s wait twogtp adds when a player crashed. For an arena game, `duration` is the game's own time in the arena plus an equal share of its chunk's overhead (the chunk's wall time beyond the durations of all its records, failure records included: starting the arena, loading the networks, and any game left without a record), shared among the chunk's stored games; a failed game's own time is subtracted and not shared, since the game is replayed, so a generation's durations still add up to its worker seconds, and `time_black`/`time_white` are each side's summed move times (a bot's `genmove` answers), to a tenth, the time charged against main time. Rows from before migration 005 have no timings;
  - the SGF, only for every `keep_every`-th generation (setting, default 10; 0 keeps none); an arena game's is built from its moves (`ArenaResult#sgf`).

  Rows are keyed by generation, round, and players, so a replayed game replaces its row.
- The schema changes only through Sequel migrations in `db/migrations/`. The runner applies pending ones when it opens the store. Add a new numbered migration for a schema change; never edit one that has run.
- `stats` and `ranking` only read: they open the experiment database read-only, so they can run beside the runner.
- Networks live in the `networks` table (the `.ann` bytes). The runner writes the current generation's networks into `work/` to play them, and the parents into `work/parents/` to breed, because both generations name their networks `0.ann`, `1.ann`, and so on. A generation's networks are dropped, in the same transaction that saves the next generation's setup, unless it is a `keep_every`-th generation. To inspect a network, export it: `ExperimentDatabase#export_networks(generation, directory)`.
- `stats NAME` prints the tables once and exits; `--watch` redraws them every 5 s until Ctrl-C; `--csv` prints one row per generation. It reads the raw settings and needs `board_size` and `features`: total weights come from `FeatureGroups.total_weights` with the experiment's feature set, and an experiment without either setting makes `stats` print `features is missing` (or `board_size is missing`) on stderr and exit 1, rather than show wrong weights.
  - Tables: Generations (the latest 50), then for the latest 10 generations Genes (each gene's median, the median layers, width, and total weights, and the min and max rows for the latest generation with births), Feature weights (the same rows for `feature_step` and one column per move feature of the experiment's set; no table without move features (`none`, or `liberties` alone), where no network has a feature weight and `feature_step` never moves), Shapes and activations (the three most common of each), and Breeding and bots (most children of one parent, parents without children, structural changes, and per bot group the best copy's rank by score with the networks above it in brackets), then the checkpoints' Benchmark.
  - Children per parent count selection: a crossover counts for both parents, a mutation or copy for the picked parent, out of the previous generation's ranked networks. The Parents column (`population.distinct_parents`) instead counts whose weights survive. Bot ranks go by score (1 + players with more points), so tied players share a rank whatever order the ranking broke the tie in. A bot group is a stored opponent (`opponents` table); its copies are named with a copy number (`Brown1`).
  - The CSV header is fixed per experiment: the tournament and population columns; `genes.GENE.min|median|max` for the five genes, `feature_step` (filled for every network), and all seven feature weights `fw_NAME` (empty where the experiment's set lacks that feature); `shape.layers|width|weights.min|median|max` (summaries, not one column per shape, which would vary); `activation.hidden|output.NAME` for all six activations; `structure.OP` for the five ops (`none` included); `parents.max_children|childless|used`; `bots.best_rank`, `bots.networks_above`, and the same two per stored bot group (`bots.Brown.best_rank`); then `benchmark.network`, `benchmark.complete`, and per opponent of the stored panel, color, and outcome (`benchmark.Brown.black.win`). Experiments with the same opponents and panel compare column by column; cells a generation lacks (genes and parents before migration 010, structure and parents in generation 0, a group with no ranked copy) are empty.
- `ExperimentStats` computes the figures (a Hash per generation) and `ExperimentStats::Report` formats them; neither prints on its own. A checkpoint counts as finished only once its benchmark is complete: stored rows equal `benchmark_games` times the opponents from `CheckpointBenchmark.opponents_for`, the same rule the runner plays by, so change it there only.
- `ranking` loops forever. Run it with a timeout or in the background.
- Games run on a `WorkerPool` (`ruby/worker_pool.rb`): `concurrency` threads, created once per experiment, each running an arena chunk (the tournament) or a `gogui-twogtp` game (the benchmark) in `sh -c` (`Process.spawn`, then `Process.wait2` on its pid; a command that cannot run exits 127, as under `system`); `next_finished` returns a job's identifier, its wall-clock seconds, and its `Process::Status`. The jobs stay in the runner's process group, so a Ctrl-C in the terminal reaches every one. `WorkerPool#terminate` keeps queued jobs from starting, as `halt` does, and sends SIGTERM to the running ones, returning how many it signalled; a thread that starts its job just after it kills that job at once, and a job already reaped is never signalled (each thread records its pid, and clears it once `wait2` returns, under one lock with the terminating flag). It is only for jobs that `exec` their program: `RunGeneration#prepare_chunk` prefixes the arena command with `exec`, so the job's pid is the arena, whose own SIGTERM handling stops its bots, while a SIGTERM to the shell running `gogui-twogtp` would leave the JVM running (macOS `sh` does not exec a last command with redirections by itself). On Ctrl-C the running games stop, the pool starts no queued game (`WorkerPool#halt`, called from the trap in `RunExperiment`), and the runner exits without scoring, leaving the unfinished games (a whole arena chunk, too) pending in the database, so resuming replays them. Ctrl-C reaches the games as well as the runner, and a killed job can come back before the trap has set `$stop_now`, so the runner (tournament and benchmark) also exits without scoring a job whose status `WorkerPool.interrupted?` calls interrupted: killed by SIGINT or SIGTERM, or exiting 130 or 143 (128 plus the signal), as `gogui-twogtp`'s JVM does on Ctrl-C. Without the flag set it says on stderr which game or chunk was interrupted and exits 130 (after Ctrl-C with the flag set the runner exits 0, though `mise run run` itself reports 130 because mise gets the SIGINT too), so killing one hung game stops the run and leaves the game pending. A shell running a command that SIGINT killed kills itself with SIGINT, and the arena dies of it, so both show as signaled. Any other end of an arena chunk, such as SIGKILL or SIGSEGV, stops the run as the scoring rules say, after storing its valid records.
- GNU Go 3.8 needs `scripts/patches/gnugo-3.8-gg-sort-empty.patch`. Without it, clang builds abort in `final_score` and during level 10 move generation. GCC builds happen to work either way. When changing how external tools are built, bump `release_id` in `scripts/install-external-tools.sh` so existing installs rebuild, then run `mise run verify`.
- The installer downloads only from the GitHub release named in `mirror_url` in `scripts/install-external-tools.sh`, never from upstream. `scripts/external-tools.txt` lists each archive's SHA-256 and upstream URL. To change an archive, edit the manifest, give `mirror_url` a new release tag (a published release's files should not change under the same tag), bump `release_id`, and run `mise run mirror-external-tools`. That task fetches from upstream and uploads to the release.

## Benchmark

- `CheckpointBenchmark` (`ruby/checkpoint_benchmark.rb`) measures progress apart from the tournament. `RunGeneration#call` runs it after the tournament of every `keep_every`-th generation (the checkpoints, whose networks are kept); with `keep_every` 0 it never runs.
- It plays the top network of the generation's final ranking (the first entry that is not a bot) against the stored panel `benchmark_opponents`, in order. `kind` is `bot` (run by `command`), `initial_champion` (generation 0's top network), or `previous_checkpoint` (the top network of generation minus `keep_every`). Generation 0 plays the bots only, and `previous_checkpoint` is skipped when it would be generation 0, which `initial_champion` already covers.
- Each opponent gets `benchmark_games` games (setting, even, default 20), half with each color: opening `k` is played once with each. The openings (`Openings.moves`) have `benchmark_opening_moves` stones (setting, default 4), drawn from the experiment seed and `k`, never orthogonally adjacent, so they are the same at every checkpoint and checkpoints compare. They go to twogtp as `-openings work/benchmark/openings/k/`.
- twogtp counts opening stones as moves, so the runner passes `-maxmoves` as `max_moves` plus the opening's stones, and the stored `length` includes them.
- With `benchmark_opening_moves` 0 there is no `-openings`, and the games against deterministic opponents (Brown, AmiGo, networks) repeat: only the GNU Go games differ, through their per-game seed.
- Scoring, from the benchmarked network's side, keeps the tournament's rules from before rules `3` (`CheckpointBenchmark#score`, on `GameResult`): the referee decides, a crashed network (benchmarked or opponent) loses, a draw has no winner, and a crashed bot, a missing referee score, another GoGui error, or a missing `.dat` is a failure with no winner, stored with its reason; a failure does not stop the run.
- Results go to `benchmark_games`, one row per game keyed by generation, opponent, opening, and `network_color` (the benchmarked network's). `winner` is `network`, `opponent`, or nil; `network` is the benchmarked network's name and `opponent_network` the opposing one as `generation:name`. The other columns are those of `games` without `scorer` and `end_reason`; no SGF is kept.
- On resume it plays only the games with no row. A row is stored before the game's files are deleted, so a crash between the two does not replay the game. Ctrl-C exits before scoring, as in the tournament, also when the interrupted game is back before the trap has run.
- Its files live in `work/benchmark/`: the exported networks as `GENERATION-NAME`, each game as `OPPONENT-OPENING-COLOR` (`.dat`, `-0.sgf`, `.err`), and the openings.
