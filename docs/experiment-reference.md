# Experiment reference

Detailed runner, scoring, storage, and benchmark behavior. Read the relevant section when changing experiments or their results. For the genome and feature settings, see [The evolving genome](genes.md) and [Go features](features.md).

## Game results

- A GoGui `.dat` file is tab-separated: `GAME RES_B RES_W RES_R ALT DUP LEN TIME_B TIME_W CPU_B CPU_W ERR ERR_MSG`.
  - Columns can be empty, so split on tabs. The runner and the benchmark do this in `ruby/game_result.rb`.
  - The runner saves twogtp's stderr to `PREFIX.err` next to the `.dat` file while the game runs. Only stderr says which program crashed ("Black program died" or "White program died").
- Each experiment stores its opponents, its benchmark panel, and its scoring when it is created (tables `opponents`, `benchmark_opponents`, and `scoring`, from `SetupExperiment::DEFAULT_OPPONENTS`, `DEFAULT_BENCHMARK`, and `DEFAULT_SCORING`), and the runner reads them from there, so changing the defaults only affects new experiments. By default every win is worth 1 point, whether the loser is a network or a bot, a draw 0, and the odd player out in a round sits out with 0. `scoring['rules']` is the version of the scoring logic (`RunGeneration::SCORING_RULES`); bump it when `score_game` or `GameResult` change what counts, and an experiment begun under other rules refuses to run. The bots play in the ranking like networks, and against each other, on purpose: their place in the ranking shows how the networks compare to them. Parents are chosen by tournament selection (`select_parent` in `ruby/run_generation.rb`): draw `tournament_size` networks (setting, default 3) with replacement and keep the highest score. Only the order of scores matters, and equal scores pick uniformly.
- Every game is area-scored with the experiment's komi (the `komi` setting, a multiple of 0.5 from −50 to 50, default 6.5, so a margin is never 0 without a draw). The runner passes it as `-komi` to every `gogui-twogtp` command, tournament and benchmark, and twogtp sends it to both players and the referee; the arena gets it as KOMI. The referee, `GameResult::REFEREE`, is GNU Go with `--chinese-rules` (the runner appends its `--seed`); GNU Go players keep their own rules. An experiment created before the setting has no `komi` and refuses to load.
- Scoring rules (agreed with the owner, in `score_game`, `ruby/game_result.rb`, and `ruby/arena_result.rb`):
  - The scorer decides: in the tournament, the arena's Tromp–Taylor count for a game between two networks, and the GNU Go referee (Chinese rules) for a game with a bot; in the benchmark, always the referee. A win (`B+` or `W+`) counts, including games stopped by the move limit, which the arena counts as the board stands, dead stones included.
  - A draw gives no points.
  - A network that crashes loses, whatever the referee said, and so does a network the arena cannot play (missing, unreadable, or not fitting the board). If neither network of an arena game can play, the game fails (`arena: neither network can play`).
  - These give no points and are logged, with the reason in their row's `failure` column: a crashed external bot, a missing referee score (`?`), any other GoGui error (an illegal move is blamed on the program that rejected it, not the one that played it), a missing or empty `.dat` file, and an arena game without a valid result line (`arena: no result`).
  - Failed games are never retried, so a broken setup stays visible.
- For a GoGui game, check `RES_R` and `ERR`, not only whether the game finished. A crashed player shows only in `ERR`, and a crashed referee only as `?` in `RES_R`. `scripts/smoke-external-tools.sh` checks both. Keep it that way when changing it.
- Brown and AmiGo play deterministically. The 5 Brown and 10 AmiGo "instances" are copies of the same opponent, so replaying a pairing with the same colors adds no information.
- GNU Go seeds its random choices from the clock unless it gets `--seed N`. The runner always passes one; outside the runner, compare GNU Go behavior with a fixed seed.

## Running experiments

- On a first run, `mise run run NAME` prompts on STDIN for settings. To start without prompts, create the experiment first; `SetupExperiment::SETTINGS` lists every setting with its default and its type (a whole number, an even whole number, or a number, and its range; `mise run new-experiment` without arguments shows them). A value that does not parse strictly is refused when the experiment is created, and a prompt asks again. The database stores settings as strings; `SetupExperiment.parse` turns them into Integers and Floats on every load, so the runner never converts them itself, and test settings must be typed too:
  ```sh
  mise run new-experiment NAME --board-size 9 --population-size 4 --hidden-layers 1 --layer-size 10 \
    --cross-over-rate 0.5 --game-length 10 --max-moves 200 --tournament-rounds 1 --keep-every 0 --seed 3
  mise run run NAME 4 one-generation
  ```
  That runs one generation of 10 pairings (9 games plus a bye for the odd player out) in about a second, which makes it a good smoke run. With seed 3, one game is between two networks and goes to the arena, and 8 go through GoGui (25 Sep 2026, and again with every feature group, the default, 26 Sep 2026); with most seeds the 4 networks meet only the 15 bots, and the arena plays nothing. `--keep-every 0` skips the benchmark, which would otherwise add 60 games at generation 0. Delete `experiments/NAME` afterwards. Running it again breeds and plays the next generation. `experiments/` is gitignored.
- `hidden_layers` and `layer_size` are generation 0's shape. `features` (default `all`) is the feature groups every network of the experiment sees: `none` (the stones alone, the control), `all`, or a comma-separated list of `shapes`, `tactics`, `last_move`, `liberties` in any order, each once; it is a `SetupExperiment::FeatureSet`, parsed strictly (by `FeatureGroups.normalize` in `ruby/feature_groups.rb`) to the genes line's form, `none` or the groups in their fixed order (`all` becomes `shapes,tactics,last_move,liberties`), which is what the database stores and what the genes lines are checked against. `meta_rate` is the τ of self-adaptive mutation, and the `initial_*` settings are the genes every generation-0 network starts with (ranges = the clamps in `lib/ann.h`): `initial_feature_step` (default 0.01, 1e-4–1) is generation 0's `feature_step`, and `initial_feature_noise` (default 0.3, 0–1), no gene, is the relative noise on generation 0's feature weights. `initial_weight_changes`, when not given, is computed at creation from the generation-0 shape and feature set as max(1, 0.0004 × total weights), the feature inputs counted (`FeatureGroups.total_weights`, which `SetupExperiment.total_weights` uses: 9×9 1×10 has 1,732 weights with `none` and 10,652 with `all`, so 4.26 changes; `features` comes before it in `SETTINGS` for that) (a `SetupExperiment::Derived` default, computed from the settings before it on both the prompt and the `new-experiment` path) and stored, so a later formula change never alters an existing experiment; a value above the network's total weights is refused. `max_hidden_layers` (default 4) and `max_layer_size` (default 200) bound the shapes structural mutation can reach; the generation-0 shape must lie within them (`max_layer_size` is checked against `layer_size` only when `hidden_layers` is above 0), and a shape above them is refused on every path: the prompts ask again, `new-experiment` fails, and loading fails. So networks of one experiment differ in shape: from generation 1 on, a mutated child can gain or lose a layer or a neuron per layer, and its `births` row has its `structure` and its new `layers` and `width`. Nothing in the runner, the arena, or the benchmark assumes the generation-0 shape except `initial_weight_changes`' check and the check that `initial-population`'s genes lines have that shape. A seeded run that exercises the genes quickly:
  ```sh
  mise run new-experiment NAME --board-size 9 --population-size 12 --hidden-layers 1 --layer-size 10 \
    --cross-over-rate 0.5 --game-length 10 --max-moves 200 --tournament-rounds 3 --keep-every 2 \
    --benchmark-games 2 --initial-structure-rate 0.3 --initial-activation-rate 0.2 \
    --max-hidden-layers 3 --max-layer-size 20 --seed 4242
  ```
  Six generations of it (concurrency 4, every feature group; 26 Sep 2026) produced all four kinds of structural change, shapes from 0×0 to 3×10 (a 0×0 network is the largest here, 79,950 weights, since all 974 inputs connect to the outputs), no failed game, 2.5–2.8 s per generation, 7–9 s with a checkpoint's benchmark, 15 s for generation 0, and the same births (every column), networks, games, rankings, and benchmark rows on a second run with the same seed. With the defaults (`initial_structure_rate` 0.02, crossover rate 0.5) a generation of 20 sees a structural change only every few generations, so a run meant to explore shapes needs a higher starting rate. Loading a database that lacks a setting fails with "… is missing"; so an experiment created before the feature settings (`features`, `initial_feature_noise`, `initial_feature_step`) does not load.
- An experiment directory holds only `experiment.sqlite3`, the scratch directory `work/`, and the executables. The runner works inside `work/`, which it empties at the start of every generation, and calls `../evo`, `../arena`, `../evolve`, and `../initial-population`. They are **copies** of the build output, made on the experiment's first run once its settings are known, so a rebuild does not change an experiment that has started; to run new code, start a new experiment. The Ruby runner is not copied: it runs from the checkout, so an experiment whose executables take other arguments than the runner passes cannot resume. One started before the genes settings (`meta_rate`, `initial_*`) is such a case: its settings lack them and its `initial-population` and `evolve` take the old arguments. Once the provenance is recorded, a missing executable stops the run instead of being copied again. The `provenance` table records what they were built from: the git revision, whether the checkout had uncommitted changes, and the external tools release.
- `RunGeneration#play_round` splits a round's games: the bye is scored at once; games between two networks go to the arena (`../arena`, scored by Tromp–Taylor, `scorer` `tromp_taylor`) in at most `concurrency` chunks, each one `WorkerPool` job with the files `arena-K.txt` (schedule, IDs from the game's file prefix), `arena-K.out`, and `arena-K.err`; games with a bot go to `gogui-twogtp`, one job each. The wait loop counts jobs. When a chunk finishes, every game in it is scored (a network that cannot play loses; a game without a valid line fails with `arena: no result`, including every game after the arena died, the chunk's files are read as UTF-8 whatever the locale, and bytes that are not UTF-8 are replaced before parsing), stored, and ranked, then the chunk's files are deleted. What an arena row holds is in the bullet on game results below; the chunk's overhead share is floored at 0. `SCORING_RULES` `2` is the version that scores network games in the arena.
- Everything but a game's files in progress lives in `experiments/NAME/experiment.sqlite3`: the settings, and each generation's round, players, standings (`rankings`), and pending games. `RunGeneration#data` loads a generation's state in the shape `data.json` used to have once per session and keeps it in memory; `save_data` replaces it in one transaction after every game and keeps what it saved, which must equal what `ExperimentDatabase#state` would load (string keys, pending games in order). On resume, `setup_complete` skips creating or breeding the population, the runner starts from the last generation in the database, and a generation's games are skipped only once `round` reaches `tournament_rounds`. A checkpoint's benchmark runs after that check too, so a resumed checkpoint finishes its benchmark. `RunGeneration#call` returns `:already_done`, which makes a `one-generation` run go on to the next generation, only when the generation played no tournament game and no benchmark game.
- At the end of every generation the runner prints its timings (`ruby/generation_timings.rb`, the monotonic clock): a summary of two or three lines, then one machine-readable line to compare runs by. Nothing is stored. The line is `timings` and `key=value` fields, seconds with three decimals, in this order and only for the parts that ran in this session: `generation=N partial=0|1 setup=S`, then per round played `round_K=S worker_round_K=S ruby_round_K=S games_round_K=N failures_round_K=N` (K from 1), then over those rounds `tournament=S worker=S ruby=S games=N failures=N`, then `benchmark=S total=S`. `setup` is creating or breeding the population and exporting the networks (on resume only the export); a round runs from queueing its first game to pairing the next round; `worker` is the summed wall time of its pool jobs (arena chunks and GoGui games, more than the round's time when they run in parallel); `ruby` is the round's time the runner spent not waiting for a job (pairing, queueing, reading results, scoring, storing); `games` counts the games scored (byes not counted) and `failures` those with a failure; `benchmark` appears for a checkpoint whenever its benchmark code ran. `partial=1` marks a generation an earlier session began (its state was already in the database): its times cover only this session, and the summary says so. A generation stopped by Ctrl-C or an error prints nothing, and so does one this session had nothing left to do in (its tournament finished and no benchmark game left, as when a `one-generation` run re-enters the last finished generation), so every timing line is a generation that ran.
- Ctrl-C during "Generating population" kills the running `evolve` too, and the runner exits quietly as it does in the tournament (with exit 130 and a message when evolve's status shows the interrupt before the trap ran). Nothing is lost: the children bred so far are in `births` and `networks`, but the generation's setup is saved only after the last child, so a resume breeds every child again from the first, with the same seeds and the same parent draws, and overwrites those rows. An interrupted and resumed run gives the same births, networks, games, rankings, and benchmark rows as an uninterrupted one (checked twice mid-breeding, 25 Sep 2026, and again with every feature group, 26 Sep 2026).
- The runner passes `-force` to twogtp, which deletes an existing `PREFIX.dat`. A game that was queued but not yet scored when the runner stopped, through GoGui or in the arena, is replayed from scratch on resume, and its `.err` is rewritten.
- Generation 0 names networks `0001.ann`, `0002.ann`, and so on. Later generations use `0.ann`, `1.ann`, and so on.
- Game results live in `experiments/NAME/experiment.sqlite3`, through `ExperimentDatabase` (`ruby/experiment_database.rb`, Sequel on SQLite). After scoring a game, the runner writes its row and deletes the game's files (`.dat`, `.sgf`, and `.err`; an arena chunk's files once all its games are stored). The row holds:
  - the players, the winner or failure, the length, the result (`referee_result`: GNU Go's for a GoGui game, the Tromp–Taylor count for an arena game), the error message (GoGui's, or `move limit exceeded` for an arena game stopped by the limit), and stderr (for an arena game, the chunk's, only when the game failed);
  - `scorer`, who decided the game: `gnugo` for a GoGui game refereed by GNU Go, `tromp_taylor` for an arena game. `ExperimentDatabase#record` refuses a row without one, and rows from before migration 009 got `gnugo`;
  - the timings. For a GoGui game, `duration` is the wall-clock seconds of the whole `gogui-twogtp` run, measured by `WorkerPool`, and `time_black`/`time_white` are the seconds each player spent answering `genmove`, from twogtp's `TIME_B`/`TIME_W`, to a tenth; the rest of `duration` is the referee, the JVM, process starts, and the other GTP commands, plus a 3 s wait twogtp adds when a player crashed. For an arena game, `duration` is the game's own time in the arena plus an equal share of its chunk's overhead (the chunk's wall time beyond its games', such as starting the arena and loading the networks), so a generation's durations still add up to its worker seconds, and `time_black`/`time_white` are the summed move times, to a tenth. Rows from before migration 005 have no timings;
  - the SGF, only for every `keep_every`-th generation (setting, default 10; 0 keeps none); an arena game's is built from its moves (`ArenaResult#sgf`).

  Rows are keyed by generation, round, and players, so a replayed game replaces its row.
- The schema changes only through Sequel migrations in `db/migrations/`. The runner applies pending ones when it opens the store. Add a new numbered migration for a schema change; never edit one that has run.
- `stats` and `ranking` only read: they open the experiment database read-only, so they can run beside the runner.
- Networks live in the `networks` table (the `.ann` bytes). The runner writes the current generation's networks into `work/` to play them, and the parents into `work/parents/` to breed, because both generations name their networks `0.ann`, `1.ann`, and so on. A generation's networks are dropped, in the same transaction that saves the next generation's setup, unless it is a `keep_every`-th generation. To inspect a network, export it: `ExperimentDatabase#export_networks(generation, directory)`.
- `stats NAME` prints the tables once and exits; `--watch` redraws them every 5 s until Ctrl-C; `--csv` prints one row per generation. It reads the raw settings and needs `board_size` and `features`: total weights come from `FeatureGroups.total_weights` with the experiment's feature set, and an experiment without either setting makes `stats` print `features is missing` (or `board_size is missing`) on stderr and exit 1, rather than show wrong weights.
  - Tables: Generations (the latest 50), then for the latest 10 generations Genes (each gene's median, the median layers, width, and total weights, and the min and max rows for the latest generation with births), Feature weights (the same rows for `feature_step` and one column per move feature of the experiment's set; no table without move features (`none`, or `liberties` alone), where no network has a feature weight and `feature_step` never moves), Shapes and activations (the three most common of each), and Breeding and bots (most children of one parent, parents without children, structural changes, and per bot group the best copy's rank by score with the networks above it in brackets), then the checkpoints' Benchmark.
  - Children per parent count selection: a crossover counts for both parents, a mutation or copy for the picked parent, out of the previous generation's ranked networks. The Parents column (`population.distinct_parents`) instead counts whose weights survive. Bot ranks go by score (1 + players with more points), so tied players share a rank whatever order the ranking broke the tie in. A bot group is a stored opponent (`opponents` table); its copies are named with a copy number (`Brown1`).
  - The CSV header is fixed per experiment: the tournament and population columns; `genes.GENE.min|median|max` for the five genes, `feature_step` (filled for every network), and all seven feature weights `fw_NAME` (empty where the experiment's set lacks that feature); `shape.layers|width|weights.min|median|max` (summaries, not one column per shape, which would vary); `activation.hidden|output.NAME` for all six activations; `structure.OP` for the five ops (`none` included); `parents.max_children|childless|used`; `bots.best_rank`, `bots.networks_above`, and the same two per stored bot group (`bots.Brown.best_rank`); then `benchmark.network`, `benchmark.complete`, and per opponent of the stored panel, color, and outcome (`benchmark.Brown.black.win`). Experiments with the same opponents and panel compare column by column; cells a generation lacks (genes and parents before migration 010, structure and parents in generation 0, a group with no ranked copy) are empty.
- `ExperimentStats` computes the figures (a Hash per generation) and `ExperimentStats::Report` formats them; neither prints on its own. A checkpoint counts as finished only once its benchmark is complete: stored rows equal `benchmark_games` times the opponents from `CheckpointBenchmark.opponents_for`, the same rule the runner plays by, so change it there only.
- `ranking` loops forever. Run it with a timeout or in the background.
- Games run on a `WorkerPool` (`ruby/worker_pool.rb`): `concurrency` threads, created once per experiment, each running a `gogui-twogtp` game or an arena chunk through `system`; `next_finished` returns a job's identifier, its wall-clock seconds, and its `Process::Status`. On Ctrl-C the running games stop, the pool starts no queued game (`WorkerPool#halt`, called from the trap in `RunExperiment`), and the runner exits without scoring, leaving the unfinished games (a whole arena chunk, too) pending in the database, so resuming replays them. Ctrl-C reaches the games as well as the runner, and a killed job can come back before the trap has set `$stop_now`, so the runner (tournament and benchmark) also exits without scoring a job whose status `WorkerPool.interrupted?` calls interrupted: killed by SIGINT or SIGTERM, or exiting 130 or 143 (128 plus the signal), as `gogui-twogtp`'s JVM does on Ctrl-C. Without the flag set it says on stderr which game or chunk was interrupted and exits 130 (after Ctrl-C with the flag set the runner exits 0, though `mise run run` itself reports 130 because mise gets the SIGINT too), so killing one hung game stops the run and leaves the game pending. A shell running a command that SIGINT killed kills itself with SIGINT, and the arena dies of it, so both show as signaled. Any other crash of the arena, such as SIGKILL or SIGSEGV, is scored: its games without a valid line fail with `arena: no result`.
- GNU Go 3.8 needs `scripts/patches/gnugo-3.8-gg-sort-empty.patch`. Without it, clang builds abort in `final_score` and during level 10 move generation. GCC builds happen to work either way. When changing how external tools are built, bump `release_id` in `scripts/install-external-tools.sh` so existing installs rebuild, then run `mise run verify`.
- The installer downloads only from the GitHub release named in `mirror_url` in `scripts/install-external-tools.sh`, never from upstream. `scripts/external-tools.txt` lists each archive's SHA-256 and upstream URL. To change an archive, edit the manifest, give `mirror_url` a new release tag (a published release's files should not change under the same tag), bump `release_id`, and run `mise run mirror-external-tools`. That task fetches from upstream and uploads to the release.

## Benchmark

- `CheckpointBenchmark` (`ruby/checkpoint_benchmark.rb`) measures progress apart from the tournament. `RunGeneration#call` runs it after the tournament of every `keep_every`-th generation (the checkpoints, whose networks are kept); with `keep_every` 0 it never runs.
- It plays the top network of the generation's final ranking (the first entry that is not a bot) against the stored panel `benchmark_opponents`, in order. `kind` is `bot` (run by `command`), `initial_champion` (generation 0's top network), or `previous_checkpoint` (the top network of generation minus `keep_every`). Generation 0 plays the bots only, and `previous_checkpoint` is skipped when it would be generation 0, which `initial_champion` already covers.
- Each opponent gets `benchmark_games` games (setting, even, default 20), half with each color: opening `k` is played once with each. The openings (`Openings.moves`) have `benchmark_opening_moves` stones (setting, default 4), drawn from the experiment seed and `k`, never orthogonally adjacent, so they are the same at every checkpoint and checkpoints compare. They go to twogtp as `-openings work/benchmark/openings/k/`.
- twogtp counts opening stones as moves, so the runner passes `-maxmoves` as `max_moves` plus the opening's stones, and the stored `length` includes them.
- With `benchmark_opening_moves` 0 there is no `-openings`, and the games against deterministic opponents (Brown, AmiGo, networks) repeat: only the GNU Go games differ, through their per-game seed.
- Scoring follows the tournament's rules from the benchmarked network's side: the referee decides, a crashed network (benchmarked or opponent) loses, a draw has no winner, and a crashed bot, a missing referee score, another GoGui error, or a missing `.dat` is a failure with no winner.
- Results go to `benchmark_games`, one row per game keyed by generation, opponent, opening, and `network_color` (the benchmarked network's). `winner` is `network`, `opponent`, or nil; `network` is the benchmarked network's name and `opponent_network` the opposing one as `generation:name`. The other columns are those of `games`; no SGF is kept.
- On resume it plays only the games with no row. A row is stored before the game's files are deleted, so a crash between the two does not replay the game. Ctrl-C exits before scoring, as in the tournament, also when the interrupted game is back before the trap has run.
- Its files live in `work/benchmark/`: the exported networks as `GENERATION-NAME`, each game as `OPPONENT-OPENING-COLOR` (`.dat`, `-0.sgf`, `.err`), and the openings.
